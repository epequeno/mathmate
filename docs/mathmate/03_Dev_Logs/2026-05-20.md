## Reactive Streaming Auto-Scrolling ✅

### What was built

**Modified files:**
- `prototype/MathMate/Sources/MathMate/Views/MainView.swift`
  - Previously, auto-scrolling was triggered by `.onChange(of: viewModel.messages.count)`. Since the message count does not change while the agent streams tokens into the last message, the scroll view would overflow and hide streaming text below the fold.
  - Added a computed property `lastMessageContentSignature` to `ChatView` that captures a unique string based on the last message's ID, its streaming text character length, and its thinking text length.
  - Subscribed to `.onChange(of: lastMessageContentSignature)` to trigger scrolling to `"bottom-anchor"` whenever a new token is appended to the message (of both thinking and content types).
  - Ensured auto-scroll triggers both when `isAtBottom` is true and when `viewModel.isLoading` is active, keeping the view perfectly and fluidly anchored to the bottom as the agent responds.

## Session Name Persistence Fix 🔧

### Bug
Session names renamed via the toolbar inline editor or sidebar context menu reverted on app restart. Two root causes:

1. **Toolbar displayed stale name** — `MainToolbarView` rendered `session.displayName` from its `let session: SessionHeader` parameter instead of `chatVM.currentSession.displayName`, so even after `saveEditedName()` updated the in-memory reference, the toolbar still showed the old name.

2. **Sidebar rename didn't propagate** — `renameSession()` persisted the new `customName` to disk but never updated `selectedSession` in `ContentView`, so on next navigation or restart the stale header was used.

### Fix
- `MainToolbarView`: Changed both breadcrumb and title text to use `chatVM.currentSession?.displayName` instead of `session.displayName`, ensuring the displayed name stays in sync with the canonical source.
- `renameSession()`: After persisting to disk, now also updates `selectedSession` when the renamed session is the currently selected one.

- `prototype/MathMate/Sources/MathMate/Views/MainView.swift`

## LaTeX Rendering Performance ✅

### What was built
Three targeted improvements to reduce main-thread pressure during streaming:

**1. Cached compiled regexes (`LaTeXNormalizer.swift`)**
- Moved all `NSRegularExpression` construction to a module-level `RE` enum with `static let` properties, compiled exactly once at app start.
- Previously every call to `normalizeDisplayMath`, `normalizeInlineMath`, `normalizeEquationEnvironment`, `normalizeAlignEnvironment`, `cleanArtifacts`, `looksLikeMath`, and `inlineMarkdownToHTML` re-compiled its regex(es) from scratch — on every streaming token, for every message bubble.
- Also migrated `inlineMarkdownToHTML` from `replacingOccurrences(of:options:.regularExpression)` to direct `NSRegularExpression.stringByReplacingMatches` calls, using the same cached instances.

**2. Debounced streaming updates (`LaTeXView.swift`)**
- Replaced direct `pushContent()` call in `updateNSView` with `schedulePush()`.
- `schedulePush` coalesces rapid SwiftUI updates into at most one render per 80 ms window using a cancellable `Task` + `Task.sleep`.
- Skips work entirely if the content string hasn't changed since the last scheduled render.
- Result: during fast streaming (~20+ tokens/sec), the WebView receives ~12 JS calls/sec instead of one per SwiftUI tick.

**3. Off-main-thread HTML rendering (`LaTeXView.swift`)**
- The CPU-heavy `LaTeXNormalizer.renderAsHTML()` (regex matching + markdown parsing) now runs on a `Task.detached(priority: .userInitiated)` background thread.
- Only the final `evaluateJavaScript` call (which requires `WKWebView`) is dispatched back to `MainActor`.

### Files changed
- `Sources/MathMate/Rendering/LaTeXNormalizer.swift` — RE cache enum, inlineMarkdownToHTML rewrite
- `Sources/MathMate/Rendering/LaTeXView.swift` — schedulePush + debounce + async rendering

### Validation
- `swift build` passes (1.5s).
- `swift test` passes (50/50).
- No behaviour changes — all existing LaTeX/markdown rendering tests pass unchanged.
