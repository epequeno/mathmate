## Architecture Planning: Visualization Intent Compiler

### Problem identified
The current `create_widget_spec` tool architecture has a fundamental flaw: it asks the model to be a JSON schema engineer. Evidence:

1. **Normalization layer is scar tissue** — `ToolExecutor` contains `normalizeNumberLineConfig`, `normalizeGeometryCanvasConfig`, `normalizeTableValuesConfig`, and `normalizeGraphFunctionConfig` that silently alias wrong field names (`fn`→`expressions`, `x`→`points`, `xs`→`xValues`, `vertices`→`polygons`). Each alias is evidence the model emitted the wrong field name.
2. **Tool description is empty** — The `config` parameter is described as `"Primitive-specific configuration"` with zero field details. The model is guessing.
3. **System prompt bloat** — `_effectiveSystemPrompt` appends an 82-line `widgetContract` block when a user mentions visualization keywords.
4. **No composition reasoning** — Models can't decide when to use a quiz card with an embedded visualization vs. a standalone graph with a hint.
5. **Schema changes break models** — Every new primitive type requires updating the system prompt and hoping the model adapts.

### Decision: Intent Compiler architecture
Instead of fine-tuning (which teaches style, not schema compliance, and breaks on schema changes), the correct approach is to **invert the responsibility boundary**: the model describes *what* to visualize in natural language, and MathMate's Intent Compiler builds the validated native primitive spec internally.

New `visualize(description, pedagogical_goal, type_hint)` tool replaces `create_widget_spec` as the primary path. The compiler does what the model can't: exact schema assembly, domain inference, pedagogical enhancement.

### MCP server as ecosystem play
Once the compiler works internally, wrapping it as an MCP server means any external AI client can use MathMate as a visualization backend. This is a platform play, not a schema fix.

### Fine-tuning explicitly deferred
Fine-tuning may become valuable for pedagogical reasoning (when to use which visualization), but that's a different problem from schema compliance. The Intent Compiler solves the schema problem without training data, without cost, and without re-fine-tuning on schema changes.

## Widget System Expressivity Review (2026-05-22)

### Assessment
Conducted a comprehensive review of the widget system's expressive range. Key finding: the current 8 native primitives cover ~30% of the visualizations a math tutor agent needs to produce. The missing 50%+ is dominated by:

1. **Annotations & labels** (largest single gap) — the agent can plot a function but can't say "here's where the maximum is" with an arrow and LaTeX label pointing to it.
2. **Composite visualizations** — no way to show two graphs side by side, or embed a graph inside a quiz card (quiz visualization is a dead placeholder icon).

4. **Polar/parametric plots** — graph primitive only does y=f(x) Cartesian; no curlies or parametric spirals.
5. **Slider rendering** — `MMSliderSpec` schema exists but has zero rendering or state wiring.

## 3D + Animation Design (2026-05-22)

### 3D Surface Primitive (`mm.surface_3d`)
**Renderer: SceneKit** — bundled with macOS, Swift-native, handles camera/lighting/mesh rendering natively.

Schema supports: `surfaceExpression` (e.g., "x^2 - y^2"), `domain`, `zRange`, space `curves`, 3D `points`, 3D `annotations` (billboarded text), `style` (surface/wireframe/both), `camera` presets (isometric/above/side/close-up), `gridResolution` (50×50 default = 2500 vertices = 4802 triangles).

Renderer design: `SCNView` + `SCNNode` hierarchy (axes as thin cylinders, surface as custom triangle mesh from expression sampling, curves as cylinder segments, points as spheres, labels as billboard-constrained `SCNText`). Camera orbit via built-in `allowsCameraControl`.

Domain inference for 3D: paraboloid ±3, saddle ±3, egg-carton ±2π, Gaussian ±3, cone ±3.

Compositing: a `mm.composite` can mix 2D graphs and 3D surfaces side by side (e.g., parabola next to its paraboloid of revolution).

### Animation Sequence Primitive (`mm.animation.sequence`)
**Not a new renderer** — an animation layer that wraps existing primitive configs and sequences through stages. Reuses `MMPrimitiveRegistry` unmodified.

Schema: `primitiveType`, `stages` array (each: `label`, `duration`, `interpolate` field paths, `config`), `loop`, `autoPlay`.

Renderer: Shows current stage via `MMPrimitiveRegistry.buildView()`. Play/pause/step/scrub controls with progress bar. Interpolation engine lerps numeric config fields between adjacent stages at 30fps with easeInOut. Strings/bools/arrays snap at stage boundaries.

Compiler auto-generation for common patterns:
- Riemann sum refinement: auto-generates n=2, 4, 8, 16, 32 stages
- Secant→tangent convergence: auto-generates a+2, a+1, a+0.5, a+0.1, a+0.01 stages
- Function transformation: f(x)→f(x+h) in 4 intermediate steps

Unlocks: limit visualization, transformation sequences, geometric proof animations, curve tracing, Riemann sum refinement, comparative before/after.

### Priority ordering for Phase 9D
1. Slider rendering (smallest scope, schema exists)
2. Animation sequences (high teaching value, reuses all renderers)
3. 3D surfaces (covers multivariable calculus)
4. Interactive geometry (drag-to-explore)
5. Statistical visuals (box/histogram/scatter)
6. Live user-placed annotations
